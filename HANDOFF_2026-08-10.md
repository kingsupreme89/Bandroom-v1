## 🔴 Real bug found, not yet fixed: "assigning a song doesn't save" (1st/2nd/3rd/4th Down cards)
User reported: the legacy "1st Down"/"2nd Down"/"3rd Down" cards (top of the Offense category,
screenshot showed them "Unassigned") don't seem linked to anything, and assigning a song to
"1st Down" didn't survive a relaunch.

Root cause, confirmed by code read: `ConfigStore.MigrateLegacyDownEvents` (`ConfigStore.cs:1318`)
runs on **every** load (called from `EnsureAllEvents`, which both `LoadOrCreate()` and
`LoadProfile()` call — i.e. every app launch and every profile switch), despite its own doc
comment claiming "One-time migration on load." Each time it runs: if the legacy "1st Down" (etc.)
entry has a song assigned, it copies that song into the canonical event ("Offense: Earned First
Down" for 1st, "Offense: Second/Third/Fourth Down" for the rest) *only if the canonical slot is
empty*, then **blanks the legacy entry's AudioFile**. So:
1. User assigns a song to the visible "1st Down" card → saves to disk correctly.
2. App relaunches → `LoadOrCreate` → `EnsureAllEvents` → `MigrateLegacyDownEvents` fires again →
   sees "1st Down" has a song → migrates it into "Offense: Earned First Down" → blanks "1st Down".
3. User sees "1st Down" reading "Unassigned" again → looks exactly like the save didn't happen.

Worse: `"Offense: Earned First Down"` (the migration target for 1st Down specifically) is itself
in `RetiredEventKeys` (`ConfigStore.cs:1246-1258`) — a set of events deliberately hidden from the
UI. Need to verify live whether an entry in that set still renders as a card when it HAS audio
(the prune-from-storage line only removes retired entries when `AudioFile` is empty, so the data
should survive) — but if the card render path also filters out anything in `RetiredEventKeys`
regardless of audio, the migrated song has *no visible card at all* to confirm/edit/clear it.
That needs a live check in the running app (assign "1st Down", relaunch, then hunt through every
category tab for a card that gained the song) before deciding the fix.

**This needs a product decision, not a blind patch** (same conclusion Cline reached on the
adjacent "1st Down never fires" bug documented in `TASK_BOARD.md`'s "Cline → Orchestrator"
section — read that section too, it's the same family of bug, possibly the same root fix closes
both). Options -- honestly the cleanest:
- Stop migrating on every load — either migrate once and mark it done (e.g. a version-stamped
  flag file), or just delete `MigrateLegacyDownEvents`'s call from the hot load path and only run
  it as an explicit one-time upgrade step.
- Or: retire "1st/2nd/3rd/4th Down" the same way `"Offense: Second Down"` etc. already are (add
  them to `RetiredEventKeys` too) so `EnsureAllEvents`'s existing prune-when-empty logic removes
  them from the list entirely once migrated, instead of leaving a permanently-reappearing empty
  zombie card. But first confirm the canonical replacement card (`"Offense: Earned First Down"`)
  actually IS reachable/editable somewhere, or the user loses the ability to assign 1st-down songs
  entirely.
- Whichever direction: also decide whether `"Offense: Earned First Down"` should come OFF
  `RetiredEventKeys` so the migrated song has a real home in the UI.

## Fixed in source, NOT yet deployed (needs app fully closed, a Release build, DLL copy into app-1.0.72)
Both in `WebMainForm.cs`:
1. `SaveTrimFromWeb`/`WebBridge.SaveTrim` gained an optional `sourceName` param so a re-trimmed
   clip is named after the song that was actually loaded into the trimmer, not whatever was
   previously assigned to the event (only mattered once fix #3 above let Trim target an
   arbitrary highlighted song instead of only the current assignment).
2. `BrowseForAudioFileFromWeb` — "Browse for file..." in the Clipper was assigning a song by its
   **original** filesystem path, never copying it into Bandroom's own library. User couldn't tell
   where browsed-in songs "landed" because they didn't land anywhere — this also meant they'd
   never show up in Clipper search and would break if the source file moved. Now runs through
   `ConfigStore.ImportIntoSongsLibrary` first (same as the native `AssignTrackForm`'s Browse
   button already did), copies into `Songs\uploaded\`.

To deploy: close Bandroom fully, `dotnet build BandAudioHook.csproj -c Release` (win-x64 target
matches the installed layout), copy the resulting `Bandroom.dll` into
`app-1.0.72\Bandroom.dll`, relaunch.
